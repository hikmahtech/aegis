# The research lane

Moved from `CLAUDE.md` so it is not loaded into every session. Read it before you change the code it describes.

Raphael's research flow, RSS feeds, the Calibre library, tracked topics, areas, story feedback, and the world, GitHub and tender watches.

- **Raphael researches through `ResearchFlow`, never inside a chat turn** (#509). `research_topic` hands the question to the flow under `research-<sha256 of the question>` and waits `research_config.wait_seconds` (45 by default) — the `BooksWriteFlow` seam — so a retried turn re-attaches and a slow run posts its answer to the agent's channel itself; a `#research` task runs the same flow through AgentTaskFlow's `research` verb. The lane's limits (depth tables, page and report characters, knowledge and note hits, the academic-terms pattern) are the `research_config` settings row (`services/research_config.py`, Admin → Research → Research limits); the tool schema caps stay in code. The flow's `agent_id` is the caller's, else the holder of the `research` capability tag (`AgentRegistryActivities.resolve_agents`), and the worker resolves that holder once at boot for `ResearchActivities`/`IntelligenceActivities` (`llm_calls` rows get NULL, never a made-up id, when nobody holds it); the synthesis prompt names the agent from `agents.name` at synthesis time. The steps live once, in `services/research.py`, shared by the chat tools (`web_search`, `read_url`, `paper_search`, `paper_read`) and the worker's `ResearchActivities`, and only a real answer is ever saved (keyed on the question, so it replaces rather than piles up). Every fetch of an untrusted URL — one a model chose, a page named or a feed publishes — goes through `services/url_guard.py`, which checks the first request AND every redirect (a public page redirecting inward was the hole); only the admin knowledge route opts out (`allow_private=True`). Guide: `docs/infrastructure.md` "The research lane".
- **AEGIS owns the RSS feed list** (#511): `channels(kind='rss')` is what `RssIngestFlow` polls, and nothing seeds it (the Miniflux seeder is gone). `feed_entries` (migration 046) records the knowledge row each entry produced, so a feed's worth is *measured* from `knowledge_injection_log` (`services/feeds.py`, Admin → Channels, `list_feeds`), never guessed. `channels.config.ingest` is `full` (default) / `abstract` / `gate` (#512). The default was measured, not assumed: the topic gate would have kept only 2 of the 10 prompt-used non-arXiv documents, so gating is opt-in and arXiv is the feed to set to `abstract`. `failing_after` failed fetches in a row (three), or no *stored* entry for `stale_after_days` (30), is a `feeds` hub finding — the thresholds are the `feeds_config` settings row (`services/feeds_config.py`, Admin → Research → Feed health; the flow reads it through `load_feeds_config`, and a feed's own `channels.config.stale_after_days` still wins). Staleness is measured from `feed_entries` (the last stored entry, else `feeds.tracking_since`), never from the cursor, which also moves past duplicates; and a failing feed resolves only after `recovered_after` (two) good fetches in a row — one good fetch, a failure under the threshold, or a run whose `record_feed_run` failed keeps the problem open with a `record: False` finding rather than resolving it. The feed itself is fetched through `url_guard` like any other untrusted URL (feedparser only parses the bytes), and `feeds` problems stay out of the hub digest. On the ingest path a `process_content` that returns `status: error` is a failure (claim released, cursor fenced), not an ingest. **The cursor is a `(published, external id)` pair** (`last_cursor` + `last_cursor_id`, #584): arXiv publishes a day as one burst sharing ONE timestamp, so a timestamp-only cursor under `max_entries_per_run` kept the first 30 and `fetch_feed`'s `<=` filter dropped the rest for good. The cap, the failure fence and the filter all compare the pair; a channel with only `last_cursor` reads a missing id as "" (the lowest), so the entries at it are offered once more and resolve as duplicates. Do not "fix" a tie with `<` or by skipping duplicates after the cap — both refill the cap with the same duplicates on every poll. The id is written before the timestamp. Guide: `docs/infrastructure.md` "Feeds".
- **Calibre is the record for books; the knowledge store holds one metadata row per book, never the text** (#510). `connectors/calibre.py` reads calibre-web over OPDS, `services/library.py` is the one implementation behind the four library tools, `ResearchFlow`'s passage step and `CalibreSyncFlow` (daily; skips unchanged books by fingerprint, refuses to delete from the index when the catalogue comes back under half its size). Two rules the code enforces: **never a host behind an SSO login page** — no host is named in code; the connector follows no redirect, so a proxy's 302 to a login page is an error, never parsed as "no books" (the #70 Miniflux trap), and a `next` or download link naming another host is refused with the credentials. And **no bulk text** — a book is read on demand, bounded, cited and not stored. Config is the Integrations page (`calibre_url/user/password`, plus the `calibre_max_book_mb`/`calibre_max_books` caps); there is NO default URL, and any of the three unset = "not configured", not an error. The read limits are the `library_config` settings row (Admin → Research → Library limits). Guide: `docs/infrastructure.md` "The Calibre library".
- **A tracked topic is a hub problem Raphael owns; its search terms are NOT** (#513, spec `docs/superpowers/specs/2026-09-12-research-hub-design.md`). The `intelligence_topics` settings row stays the registry the scans and the RSS gate read, and they read it differently (#585): **an intel scan searches each tracked topic ONCE, by its name** (`load_tracked_topics` → `tracked_topic_names`), while a topic's queries are its **match** terms (`Topic.terms`), used by the RSS gate, curiosity and the rounds. Searching every term sent ~110 SearXNG queries per scan for 20 topics, and the configured topics, searched first, filled all 20 result slots, so no tracked topic was ever scored. `search_source` therefore takes the topics' results round-robin (`interleave`, starting at a topic that rotates by day) before trimming to `max_results`, so every topic that returned something gets a share of the one scoring call. The problem (class `topic`, source `research`) is the round of news, and every article naming a term is an occurrence keyed on its URL (`services/research_topics.py`, the one implementation behind `track_topic`, `untrack_topic`, the curiosity "track this?" card and `attach_topic_items`). A round earns a Todoist task only at its threshold — the topic's own `threshold`, else its priority's number in the `research_topics_config` row (`services/topics_config.py`; the projector skips it until `metadata.attention`) — and **completing the task resolves AND closes the round at once**, so the next article opens a fresh round rather than reopening a task the user just dismissed. Research tasks are `#research @raphael @next` (the agent sweep may research them); feed findings are `#feeds @raphael @next` (excluded from the sweep, verb `None`). Both land in the Inbox, so clarify must treat them as hub-owned *before* its `#research → reference` rule — the status-block marker in the description is the race-free signal, since the problem lookup misses a task still linked by its outbox temp id. The assignee label is resolved from the `research` tag holder (`hub_project._assignee_label`), never a literal id: with no holder the task is created with its GTD state label alone and `hub_project_owner_unresolved` is logged. The registry itself is also edited whole on Admin → Research (`GET/PUT /api/admin/research/topics`, `research_topics.save_registry`), under the same advisory lock `track`/`untrack` take.
- **Areas report what changed, not how much was written** (#674, `services/research_areas.py`). An area groups topics under `areas` in the SAME `intelligence_topics` row (never a second registry), with the user's own "why", a `cadence` (`daily` brief, `weekly` brief on `research_topics_config.weekly_day`, `vault` = the week's journal note, never interrupts) and a `cap`. Every registry write keeps `areas` unless the body carries it (`_save_registry` merges), so `track`/`untrack` and a topics-only PUT never wipe them. A topic in an area **never earns a task from item count** (`attach_items` skips `_check_attention`) — volume measured the internet, and 13 such tasks were raised and none completed. The morning brief (`BriefingActivities._gather_areas`) folds an area's items into stories by title-word overlap (no model; keyed on the earliest URL), drops story keys already shown (`briefing_state.seen_story_keys`), and makes one `think()` per area (purpose `area_digest`) that may pick none; a failed or unreadable answer falls back to the most-carried stories so the brief always ships. At most `brief_items` stories per brief, spent in the areas' order, rendered as their own block after the summary (like the failure block) and withheld from the summary prompt. With any area configured the old `intel` and `topics` sections, and scan finds in `collected`, step aside; with none, the brief is unchanged.
- **The world watch turns Quantamentry's changes into area items, with no model** (#676, `services/world_watch.py`, `connectors/quantamentry.py`, `WorldWatchFlow` on the `world-watch-daily` row, before the brief). It reads `/api/scores` and `/api/cb-calendar` (`X-API-Key` = the API's `QDP_API_KEY`; `quantamentry_url`/`quantamentry_api_key` on the Integrations page, read every run) and files a regime shift, a 7-day move of `move_points`, a watched bank's meeting within `meeting_days` or its stance moving `stance_delta` as items on ONE tracked topic (`research_topics.attach_to_topic`, no term match, no task), which the user puts in an area. Each item's URL is keyed on the event (regime date, the move's ISO week, the meeting date), so re-runs attach nothing twice. Scores older than `stale_days` file nothing and count as a `connector_health` failure. Two lists, because the calendar covers 14 banks and **not the RBI**: `countries` for scores, `banks` (by country ISO) for meetings. Positive stance delta = hawkish. A topic nobody tracks attaches nothing (`missing_topic`), never a round no area can reach.
- **A story's verdict is the owner's reaction on ITS OWN message** (#675). After the brief is sent, `BriefingActivities.post_area_stories` posts each area story as its own reply in the brief's thread (the brief's `delivery_ref` is the root) and records every story shown — vault ones too, unposted — in `area_stories` (migration 053, `story_key` unique, `(channel, ts)` indexed). A reaction on the brief itself would be a verdict on seven stories at once, which is why they are separate messages. comms forwards every OWNER reaction on a message the owner did not write to `POST /api/admin/research/story-feedback`, without fetching the message body; core (`research_areas.record_verdict`) keeps it only when the `(channel, ts)` is a story and the reaction is in `VERDICTS` (👍-ish = up, 👎-ish = down, the latest wins). The judge prompt carries the area's last 30 days of 👍 and 👎 titles (`recent_feedback`) — its only ground truth about its own taste. On `feed_review_day` the brief adds a per-area scorecard (`area_scorecard_line`: shown · 👍 · 👎 · saved to raindrop, and the areas with no 👍 or save in 60 days). Both flow steps sit behind `workflow.patched("daily-briefing-area-feedback")`.
- **GitHub signals are two reads, one scheduled and one on demand** (#677, `connectors/github.py`, `services/github_signals.py`). `GithubRisingFlow` (`github-rising-weekly`, Saturday so Sunday's weekly digest has it) searches each GitHub topic in the row's config for repos created in the last `window_days` with `min_stars`, most-starred first, and files `per_topic` of each as items on ONE tracked topic via `attach_to_topic` — keyed on the repo URL, so a repo is filed once, ever; a topic whose search fails is skipped and named in `failed_topics`, never fatal. The `github_issues` chat tool (read-only, MCP-listed, Raphael's) searches one repo's issues most-reacted first, narrowed by `focus` (`bug` / `performance` / `production` / `any`, see `FOCUS`). Both use the optional `github_token` integration; unset is unauthenticated, which GitHub caps at 10 searches a minute — the connector names a zero-budget 403 "rate limited".
- **The tender watch reads GeM only, and filters on the bid's own title** (#673, `connectors/gem.py`, `services/tender_watch.py`, `TenderWatchFlow` on `tender-watch-daily`). GeM's public all-bids page posts `payload` + the page's `csrf_bd_gem_nk` token (with its session cookie) to `/all-bids-data`; `robots.txt` allows both and there is no captcha. CPPP is NOT read: its public listing is the latest ten and ignores the page number, and its search needs a captcha — never automate past one. MahaTenders is NOT read: its `robots.txt` is `Disallow: /`. GeM's full-text search is loose ("MIS" returned an EMISSIVITY coating, "GIS" stationery, live 2026-09-25), so a bid is kept only when its title names one of `title_terms` (`names_a_term`: a term in capitals is a case-sensitive whole word, so "IT" is not "Items"; any other matches at a word start, so "digiti" catches digitisation), it closes at least `min_days_left` away, and it is filed once, keyed on its `showbidDocument/<b_id>` URL. A keyword whose search fails is named in `failed_topics`; only when every keyword fails is `connector_health` told.
