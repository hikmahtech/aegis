# Money: the books and the trading desk

Moved from `CLAUDE.md` so it is not loaded into every session. Read it before you change the code it describes.

Maou's ledger (hledger journal, Postgres index, chat tools, chart of accounts) and the paper trading desk.

- **The books (Maou's ledger):** `core/src/aegis/services/books.py` (block render/parse, rules, repo sync, the allowlisted read-only `hledger` runner) + `services/bank_parsers.py` (deterministic parsers, tried before the LLM) + `services/journal_index.py` (`finance.journal_index` — idempotency on the Gmail message id, receipt↔bank matching, dues dedupe) + `services/tools/ledger.py` (the four chat tools: `ledger_query`, `ledger_post`, `ledger_reclassify`, `ledger_add_rule`). **The journal is the record and Postgres is only the index**, so never treat an amount in `journal_index` as authoritative — run hledger. Core and worker share ONE checkout at `books_path`, serialised by an flock on `.aegis.lock`, so every write goes through `books.py`; a hand-rolled file write skips the `hledger check --strict` guard and its revert. **A chat tool validates a write and does not perform it** (#388): the three writers hand it to `BooksWriteFlow` under a workflow id derived from the same content hash that makes the write idempotent, wait `LEDGER_WRITE_WAIT_S` (20s, ~4x the measured fast path) and relay what it says — so a retried turn re-attaches instead of writing twice, and a write that outlasts the wait reports itself to the agent's channel. Both sides call `services/ledger_write.py`, which is the only implementation of the three writes; putting one back in the tool would leave a write the chat loop still cannot cancel. An empty `books_repo_url` means events are indexed and never posted — and such a row is deliberately **not** stamped `parsed.version = 2`, so the weekly sweep replays the whole backlog once a repo is configured; stamping it would strand those payments outside the journal and let a later counterpart post a duplicate block. The whole money lane is gated on `money_hygiene_enabled`. **`parse_money_email` will not pay for an extraction on mail with no currency token in it** (`bank_parsers.has_money_shape`, indexed `parser=no_amount`): triage correctly tags NSE/BSE alerts, GST notices, Groww digests and KDP reports as `financial`, and the money lane used to spend a ~1,600-token call on each to conclude nothing — 324 extractions burned 522,846 tokens on 2026-09-05 and tripped the governor's kill switch, which blocks EVERY LLM call in AEGIS, email triage included. The gate turns away 71% of extractions and loses no real event. Keep it **case-sensitive** (`Rs` under IGNORECASE matches inside "hours"/"years") and keep it **permissive** — one wasted call is cheaper than a lost transaction, which is why there is no trailing `\b` on the letter codes (AWS writes `INR2,068.12`). **`capture_due` is the only place a money event may interrupt the user, and it holds three guards that live prod noise put there** (all on the first day of real mail, 2026-09-05): a zero invoice is not a bill; an already-tasked due with the same amount, currency and due date is the same obligation under another name (Google Pay mirrors billers); and a mail that says the money moves by itself (`bank_parsers.is_autopay`) is a heads-up, not a chore. Each one still indexes the event and still reaches the brief — they only withhold the Todoist task. The autopay guard is safe **because a `failed` event still tasks**: that is what catches an automatic debit that did not go through, so never extend the autopay skip to `failed`. **A due's Todoist task is a projection of it, never the due itself** (#449/#450): `post_money_event` used to gate `mark_due_paid` on the task closing, and since `mark_due_paid` has one caller that nothing re-drives, every close failure was permanent — an `item-…` ref queues no completion and a deleted task is a permanent 4xx, and each left a paid bill in every "dues open" count forever. (A *retryable* failure is fine — it queues to the outbox and reports True.) Whether Todoist accepted the close is not evidence about whether the money moved, so the payment settles the due and the close is best-effort; an unclosed task logs `money_due_task_unclosed` and a human can close it. The same rule the problem hub enforces for `problems.todoist_task_id` — and the general form is that a check about *noise* must never decide what the *record* says. **A ticked-off bill counts as paid, in the counts only:** `journal_index.OPEN_DUE_SQL` leaves out a due whose task is completed in the mirror (read every time, so un-ticking reopens it), a due with no date, and an untasked due two weeks past its date. `find_open_due` ignores all three, so a later payment still links to its due. **Two rules in the tools are load-bearing and must not be "simplified":** `books.run_hledger` polices caller arguments with an **exact-match option allowlist**, never a deny-list — hledger bundles short flags (`-Ef<path>` reads a file, `-No<path>` WRITES one), abbreviates long ones (`--fil=`) and splices `@argsfile` contents in as arguments, so every deny-prefix list is bypassable; and `ledger_post`'s msgid is a SHA-256 of the rendered block, not a uuid4, so a write that outlived the chat loop's timeout and is retried finds its own block instead of posting the transaction twice. **Granting the four tools is a DB write, not a code change**: `config/seed/agents.yaml` only seeds an agent that has no `metadata.tool_set` yet (`AGENT_TOOL_SETS` seeds nothing and nothing reads it at runtime, #579), so a running deployment needs the `agents.metadata.tool_set` update in `docs/infrastructure.md`. Statement reconciliation is a second spec, `docs/superpowers/specs/2026-09-07-statement-reconciliation-design.md` — steps 1-3 (parsers, matcher) are built, and its **§15 amendment puts the rest on the problem hub**: findings through `hub_watch.reconcile_findings` so a row that later matches resolves itself, and deterministic grouping so ~959 unmatched rows are one problem per account rather than 959 tasks. **Money problems are Maou's:** `hub_project` picks a task's owner by the source of the problem's first occurrence, so a `money` problem becomes a `#money @maou @next` task in the `personal` project of `books_todoist_projects` (the Inbox when unset), and the agent sweep skips `#money`. Completing one acknowledges its finding (`statement_findings._acknowledged`): later runs stay quiet until a row or statement period it has not seen turns up, and a finding about its subject alone (an unscoped account, a missing rate, a bad file) stays acknowledged. Un-ticking a money task does not undo that: its problem stays resolved while the task is open again (a due, by contrast, reopens on an un-tick, because its count reads the mirror every time). **The chart of accounts is configuration, not code** (#561, spec §4's 2026-09-13 amendment): which sets of books exist, their labels, the account-name **segment** that marks each one's accounts, their unknown accounts and every category → account mapping live in the `settings` row keyed `books_chart`, read on every post. `services/books_chart.py` is the one owner — lenient `merge`, strict `validate`, and a `Chart` object carrying `resolve`/`unknown`/`account_for`/`entity_of` so nothing re-derives "which set of books is this?". `books.account_for` and `books.account_entity` take the chart as a **required** argument (no default, so a call site that forgets is a test failure, not a transaction filed under the wrong entity), `post_event` takes a keyword-only `chart`, and `books.UNKNOWN`/`_ACCOUNT_MAP`/`_INCOME_CATEGORIES` are gone. The default entity's segment is **empty**, which is what makes it own every expense and income account no other entity claims; assets, liabilities and equity stay entity-NEUTRAL (`entity_of` returns None), which is what four cross-entity guards return early on. `MoneyEvent.entity` is a validated `str`, never checked against the chart — the worker, the chat tools and the tests all build events with no pool — so an unconfigured name resolves to the default entity at posting time, exactly as anything but `hikmah` did before. `DEFAULT_CHART` names nobody (one entity, `personal`, generic categories); migration 049 seeds a live deployment with what the constants carried. Admin **Money** page → *Its entities* (`GET/PUT /api/admin/money/chart`, `ChartPanel.tsx`). The currency is `settings.home_currency` on `BooksConfig.currency` — `render_manual`, `cleared_movement_sync`'s `-X`, `ledger_write`'s index row, `event_for` and `match_statements` all read it; `bank_parsers.py` keeps its `"INR"` literals, because those are facts about the Indian bank mail those parsers read, not configuration. Spec: `docs/superpowers/specs/2026-09-05-maou-books-design.md`; setup and backfill: `docs/infrastructure.md`. **Maou's trading desk** (paper mode; spec `docs/superpowers/specs/2026-09-12-maou-trading-desk-design.md`) copies the trading system's `trade_decisions` each weekday from ansaar-data, sizes them into whole-share orders against `capital`, fills them on paper at Yahoo's open — `fill_at`, which is config and still accepts `close` — and scores them against SHARIABEES in the monthly close (`services/desk_math.py` is the arithmetic, `services/trading_desk.py` the run). Two rules are load-bearing: **a stored close is never overwritten**, because Yahoo rewrites past closes after a split, so the first fetch of a day is the only raw price the desk will ever see — which is why today's bar is stored for its OPEN alone (settled at 09:15) and never its close (the live price, still moving), and why the plan must be made BEFORE the market opens: an order planned at 11:00 and filled at that day's 09:15 open would have paid a price struck before the decision existed, so `_tick` skips planning once today has an open and raises `desk_plan_skipped` so the lost day is a problem the next planning run resolves (#593); and **a day's findings are stored with its plan**, so a rerun after ansaar recovers cannot resolve a problem that is still true for that day. Two more: Yahoo returning bars does **not** mean every day is priced — it often sends a bar whose `close` is None — so the ansaar fallback is **per day, not per window**, and the pending-order lock is **per symbol**, because one order nobody can fill must not stop every other name trading; the names a plan held back are listed in its `skipped`. **The monthly score has two readings and they are not interchangeable:** the headline is the gap to the whole benchmark (what the same money would have earned just buying SHARIABEES), and the `desk_below_expectation` alarm is judged only on the gap **per rupee actually at risk** — the desk's weekly return divided by its invested share, minus the benchmark's. The desk holds about a third of its capital (the pipeline's own heat) and the benchmark holds all of it, so judging the alarm on the headline gap fires it at twelve weeks in any rising market whatever the picking does. Dividing by the share, not just subtracting a scaled benchmark, is what makes it comparable to `expected_excess_pa`, which is a fully-invested backtest figure. `target_exposure` (#669, unset = follow the pipeline) makes the desk invest that share instead: `desk_math.scale_to_exposure` rescales the rows `check_decisions` passed, in proportion and at most `max_order_pct` a name, and the plan's `note` says from what to what; the alarm still divides by the real invested share, so it holds. On stale or odd decisions it trades nothing and raises a `#money` task. A held asset class that is simply missing from the day's decisions is not odd (#699): the ETF sleeve holds one name, so every exit empties it. The desk trades the rows that came, leaves that class's positions alone (skipped as `class_missing`, still counted in the portfolio value), still raises the finding, and sells the class once it has had no rows for `desk_math.MISSING_DAYS_BEFORE_EXIT` (3) decision days running. Freezing the whole day over it froze the desk daily until an ETF row came back. But **a stated risk halt flattens the book instead of freezing it**: when ansaar's `meta.halted` says the pipeline's risk manager stopped trading, the desk sells every holding (outcome `flattened`) rather than staying fully invested against a risk manager that has pulled out. It never reads a halt into silence: an empty day with no halt stated, an older ansaar, or a failed call all stay `held_stale`, because a pipeline failure looks exactly the same and dumping the portfolio over a glitch is the failure the checks exist to rule out. **Its market is configuration, not code** (spec §12): the exchange calendar (`calendar_symbol` — the symbol whose bars ARE the trading days), the clock, the ticker suffix, the currency, the financial year's start month and the tax rates all live in the `trading-desk-daily` activities row, read on every run, and `desk_math.Rules`'s defaults name none of them — the same rule as `email_triage_rules` and `project_repo_map`, which ship empty rather than carrying one operator's senders and repos. `config/seed/activities.yaml` holds the EXAMPLE (India, the NSE, rupees). **With no `calendar_symbol` the desk does nothing and says nothing** — no finding, no task, and no fallback to anyone's exchange, because it cannot tell a market day from a holiday and a guessed one would place paper orders on a day the market was shut. Three keys dropped a currency from their names (`sell_charge_inr`/`ltcg_rate`/`ltcg_exemption_inr` → `sell_charge`/`long_term_rate`/`long_term_exemption`) and `Rules.from_config` reads BOTH, newest first: `schedule_sync` re-reads that row every few minutes, so no ordering of the deploy and the config write would have closed the gap. Migration 048 renames the keys in a live row and fills its market with exactly what the code used to hardcode. Set it all on the admin Trading desk page (`GET/PUT /api/admin/money/desk/rules`, `services/desk_rules.py`) — a merge that leaves the knobs it does not show alone, lenient on read and strict (400) on write. The seed ships the activity inactive. **`capital` is the one setting that stops being editable** (#526): `desk_math.replay` starts the book from it on every past day, so changing it once an order has filled would restate the whole history — cash, value and every weekly gap — so `desk_rules.save` refuses it with a reason and the form greys the field (`capital_locked`). The proper answer is a deposits table, where a change is an event rather than a retrospective edit; until then, refusing is the honest one. **What the desk says about itself is load-bearing too**, and three of its statements were not: money reaches `numeric` through `Decimal(str(...))` and not a rounded float, because `round(24.04, 4)` is a float 24.04 is not and asyncpg stored the whole binary expansion (#540); `filled` and `pending_checked` are reported on **every** path through the fill step, because a missing key reads as "the step never ran" rather than "there was nothing to fill" (#565); and a morning whose newest market day is one the desk already planned, with no bar for the market's last expected trading day, is counted as an `idle_weekday` and totalled as `idle_weekdays` in the month close (#525) — a market holiday reads exactly the same, so it raises no problem and the six-day `stale_calendar_days` alarm is still what escalates. A past day with only a stored **open** is a market day too (`desk_math.market_days`, #667): Yahoo sometimes blanks a traded day's bar for good, and the open the desk kept from that day's own post-open run is the proof the session happened; today still needs a close. The market's own week comes from its bars (`desk_math.trading_week`), never a hardcoded Monday-to-Friday. A **benchmark** that stops being priced gets the same `desk_price_missing` finding a holding gets (#524): without it `benchmark_values` returns an empty series, the label reads "too early" for ever and the score silently stops meaning anything.

## Handing the books to another service

`money_fanout_enabled` (Integrations → Features, on unless set to false) controls whether email
triage hands money mail to `MoneyProcessFlow`. It is read on every triage run. Turning it off,
together with deactivating the money schedules (`receipt-ingest-weekly`, `money-brief-weekly`,
`money-close-monthly`, `money-statements-reconcile`), stops this deployment writing the journal
while the trading desk and everything else keep running. Do not use `money_hygiene_enabled` or
remove the `finance` tag for this: both also stop the trading desk and other lanes.
