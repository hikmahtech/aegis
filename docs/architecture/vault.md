# The Obsidian vault

Moved from `CLAUDE.md` so it is not loaded into every session. Read it before you change the code it describes.

How AEGIS writes to the owner's Obsidian vault, the `vault_layout` row, the journal prompt and the `me/` record.

- **The user's Obsidian vault is the owner's record; the knowledge store is only its index** (#514, spec `docs/superpowers/specs/2026-09-12-raphael-notes-design.md`). The journal belongs to the `gtd` holder (`notes.JOURNAL_OWNER_TAG`); research answers belong to the `research` holder. `services/notes.py` is the ONLY writer (checkout at `notes_path` beside the books, the books git layer reused), and three rules there are load-bearing. **Insert-only:** a write creates a note or inserts ONE contiguous block into it — a journal entry as a `- <tag> <label> %% aegis:<key> %%` bullet with the text as an indented outline under it (`body_outline`: a prose paragraph is one bullet, the daylog fallback's `Label:` lines keep their items nested) at the end of the note's own section (found by heading text at any level, ending at the next heading, `---` or code fence), anything else at the end — and `_apply` refuses any text that is not the old text with exactly one block inserted (`is_one_insertion`); a note already carrying the marker is a no-op. Never rewrite, reorder or delete a line, because the user edits the same files from the phone. **A write counts only once pushed:** `obsidian-git` auto-commits from the device, so a rejected push or a conflicting rebase drops AEGIS's own unpushed commit, pulls fresh and re-applies ONCE, then reports; never force-push, and never leave a divergent commit in the checkout. **Encrypted blocks never leave the file:** meld-encrypt keeps ciphertext between `%%🔐` and `🔐%%` inside ordinary notes, so `strip_encrypted` runs before anything is indexed, shown by `note_read`, or sent to a model. **Where the notes go is config, not code** (the OSS audit): the `vault_layout` settings row (`services/vault_layout.py`, admin **Vault** page, `GET/PUT /api/admin/notes/layout`, lenient `merge` / strict `validate` as the email rules) holds the agent's folder (`agent_dir`), the questions folder, the journal's folders, file-name formats, live folders, templates, section headings and labels per kind, the week rule (`week_start`, `week_numbering` — one definition, `vault_layout.week_bounds`, shared by the note names and `flows/daylog.rollup_window`, because the rollup's label is the marker key), the block's tag and indent (the reader `split_section` takes the same indent), the index's skip list, the deterministic day log's wording (`language`) and a few switches. Its defaults are the previous hardcoded conventions except the tag (`raphael/`, `journal/<YYYY>/<NN. Mon>/DD MMM YY.md`, `W<ww> MMM YY.md` in the week's Monday folder, the month's folder note, tab indents, ISO Monday weeks), and the tag was `#raphael` and is now `#aegis/{agent}` (the writing agent's id fills the placeholder; with no agent it is `#aegis`), so a deployment with no row behaves as before apart from the tag on new blocks — old blocks keep theirs and still read, because every reader finds a block by its marker; `tests/core/test_notes.py`'s literal paths are the proof. Every function in `notes.py` takes a `Layout` (on the `Append`, set by whichever builder made it — `journal_append`, `question_append`, `notes_write.build_append`), the write gate's journal regexes are GENERATED from the layout (never a second hand-typed copy), and the worker/tools load it from the pool at call time (30s cache, invalidated on save). **A changed layout keeps the one before it as `previous`**: `_apply` treats the old paths as "marker already there" and `read_journal_days_sync` reads them too, so a re-run or backfill after a change writes nothing twice, and nothing is ever moved. The commit author is the owning agent's `agents.name` (`author_for`), never a literal; a flow started with no `agent_id` resolves the `gtd` holder for a journal write and the `research` holder for a chat note. A live periodic-notes note in the kind's `live_folder` takes the write when it already exists and is never created. With the vault configured, `DayLogFlow` appends to the journal instead of filing `daylog` rows (a vault error, or a kind switched off, falls back to the row, so no day is lost) and rollups read the journal notes. `WeeklyReviewFlow` files its review in the week's note through the same writer (`slot="review"`, key `review:<week>`), best-effort and reported as `vault` in its result; the step is behind `workflow.patched(PATCH_FILE_IN_VAULT)`, so a run in flight across the deploy skips it and says `skipped`. Unconfigured (`notes_repo_url` + `notes_deploy_key`), everything behaves as before. Chat writes go through `NotesWriteFlow` + `services/notes_write.py`, the `BooksWriteFlow` seam. Only a genuine conflict (a non-fast-forward push, a conflicting rebase) is a `NotesConflict` and earns the retry; any other git failure is a `NotesError` at once, with a short reason of ours and no URL or stderr in it. The index skips `questions_dir` (ResearchFlow's answers are already `aegis://research/<hash>` rows), `NotesBackfillFlow` runs weekly to file any day whose vault write fell back to its knowledge row — looking only at rows filed in the last `since_days` (14), because the pre-vault rows are still in the store and rereading them would put back a block the user deleted from an old note (a hand-started run defaults to 0, every row) — and a date written into a note, and the day the daylog logs, are on the user's clock (`services/user_time.py`, the `user_timezone` row, validated by `GET/PUT /api/admin/preferences/timezone`): `DayLogFlow` logs the LAST COMPLETE local day (`logged_day`: the local date of its clock, converted by the `daylog_local_day` activity, minus one, minus `day_offset`), and the rollups anchor on the same day, so the crons can sit at any time after local midnight east or west of UTC — the old "run's own UTC date" rule logged the day that had just STARTED for anyone west of UTC. `JournalPromptFlow` (`journal-prompt-daily`, ships inactive) is the gap prompt: when the day the daylog logged holds fewer than `min_words` of the user's own words (`services/journal_prompt.py` leaves out every `%% aegis:` block, the frontmatter, headings, empty bullets, checkbox lines and the day template's text, and `journal_gap_check` reads from a STRICT pull, because a stale copy cannot say nobody wrote), it sends one `private` `input` card as `journal-prompt-<day>` with REJECT_DUPLICATE, whose hook `file_journal_answer` files the answer with no model as a `selfreport:<day>` block, one bullet per typed line, and then `journal_prompt.blank_answer` sets `interactions.response` to `{"value": "", "filed": <path>}`; `NotesBackfillFlow` files and blanks any answer whose filing failed. **The `me/` record** (vault record spec §5, `services/record.py`) is the source of every agent's `user` persona document while `record.enabled` is on: `NotesSyncFlow` compiles it hourly behind `PATCH_COMPILE_RECORD` through `apply_profile_patch(source='vault_record', allow_shrink=True)`, writing a row only when its text changed, the persona PUT answers 409 for a change to `user`, and the weekly persona draft stands down in `check_profile_budget`; the seed (`services/record_seed.py`, `RecordSeedFlow`, hand-started) writes each draft once as `<name>.draft.md` with `Append(record=True, create_only=True)`, the only record write AEGIS makes until phase 7. Guide: `docs/infrastructure.md` "The vault".
