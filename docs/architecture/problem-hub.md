# The problem hub

Moved from `CLAUDE.md` so it is not loaded into every session. Read it before you change the code it describes.

How v1's own findings become problems and tasks, and how groups fold them together.

- **The infra lane is not here any more.** On 2026-10-08 homelab alerts, alert investigation (`AlertInvestigationFlow`), the swarm heartbeat, service drift, the certificate radar, automatic restarts, runbooks, deploy and maintenance windows (`service_state`), outage windows, settle windows and Gate-2 decision cards moved to the DevOps vertical (a2-devops). The sources `alertmanager`, `heartbeat`, `drift` and `investigation`, and the statuses `fixing` and `suppressed`, went with them. The `service_state` table stays until a later change drops it after a dump; nothing reads or writes it. The Problems page's Mute went too (`POST /problems/{id}/mute`); a mute set before then still holds until it runs out, and nothing sets a new one.
- **The problem hub owns problem identity** (spec `docs/superpowers/specs/2026-09-07-problem-hub-design.md`; `core/src/aegis/services/hub.py` + `hub_project.py`). Every operational finding is an `Event` ingested by `hub.ingest_event`; one open `problems` row per `correlation_key`, every occurrence, resolution or note a `problem_events` row, idempotent on `(source, external_id)`. The producers are v1's own: the flow-health and delivery watchdogs, expiry, social, the LLM spend guard, connectors, money, feeds, research, chat, sessions and manual reports. The Todoist task is a projection (`hub_project.project`), never the identity: do not look a problem up by task title. Every source projects on sight. Watchdogs resolve what they stop finding (`hub_watch.reconcile_findings`). New producer = build an `Event`, call `ingest_event`, and add its source to `SOURCES`, which is a closed vocabulary that raises on anything else. **A dead connector is a problem too, and one Slack ping is not a record** (#571): `services/connector_health.py` runs the connector set through `hub_watch.reconcile_findings` as `connectordown` findings (source `connector`, subject the connector name), so recovery resolves the problem instead of a flag deciding — a flag cannot tell "recovered" from "nobody looked", the absence of a finding can. `alerted` still suppresses repeat *pings* only. Two rules there: the sweep reads **every** `connector_health:*` row rather than the one being recorded, because `reconcile_findings` resolves any problem of its classes absent from the findings it is handed (so one connector's state would close every other connector's problem); and the row stores `down`, because the threshold is a per-call argument and a bare count says nothing about whether another connector is past its own. **A `@code` task gets a problem too** — `hub_project.ensure_problem_for_task` mints a `manual` one, which is what gives a hand-written task a session registry (`work_sessions`), a timeline and a plan checklist; call it rather than writing a second "create a problem for this task" block.
- **The same failure on many entities is ONE problem** (`core/src/aegis/services/hub_group.py`). Six Postiz posts wedged in one queue were six problems and six Todoist tasks. A **group** problem carries `group_key = '{class}:{subject_kind}'` and a correlation key of `'{class}:{subject_kind}:*'`, and `ingest_event` gives it every later *occurrence* of that class whose own key has no problem — so the seventh stuck post joins the group instead of opening a seventh task. `HubSweepFlow` proposes one: `find_group_candidates` (three or more live, ungrouped problems of one class and kind) → `judge_group` (one billed `think()` call, NO_RETRY; a refusal or a failure leaves them separate) → `apply_group` (folds via `merge_problems`, retires the swallowed tasks, renames the survivor, says so in Slack). Three rules the code enforces rather than trusts: a group never spans classes; class `manual` is never groupable (those are hand-written tasks, and folding them would move one task's sessions and PR links onto another); and `hub_watch.reconcile_findings` resolves a group only when its watchdog stops finding **any** member, because a group's subject `*` is never among the findings. A "no" verdict is cached in `settings.hub_group_verdicts` until the cluster grows, so the sweep does not re-price the same question every five minutes.
