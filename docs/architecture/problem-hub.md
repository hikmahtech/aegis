# The problem hub

Moved from `CLAUDE.md` so it is not loaded into every session. Read it before you change the code it describes.

How alerts and findings become problems, tasks and investigations, and how groups and outages fold them together.

- **The problem hub owns alert identity** (spec `docs/superpowers/specs/2026-09-07-problem-hub-design.md`; `core/src/aegis/services/hub.py` + `hub_project.py`). Every operational signal is an `Event` ingested by `hub.ingest_event` (worker: `HubActivities.ingest_alert`); one open `problems` row per `correlation_key`, every occurrence/resolution/report a `problem_events` row, idempotent on `(source, external_id)`. The hub decides — `IngestResult.investigate` — and the producer starts `AlertInvestigationFlow`; the flow never dedupes, never captures a task, and records its own transitions with `record_investigation`. The Todoist task is a projection (`hub_project.project`), never the identity: do not look a problem up by task title or fingerprint. **A blip earns no task** (#537): a problem raised by one of the two producers OUTSIDE AEGIS that send their own resolution (`alertmanager`, `heartbeat`) waits out its class's `hub.verify_seconds` before it is projected — a clock, not a count, because a five-minute blip occurs five times — and one that resolves inside the window never earns a task at all. A recurrence is exempt: `reopen` keeps `first_seen_at`, so a return within `REOPEN_WINDOW` projects at once (later, it is a `rollover` and waits like a first sighting). **The flow learns the deferred task's id when its verification delay ends** (`HubActivities.project_problem`) — that delay IS the window, so projecting then mints the task; without it every note before step 4, the auto-restart evidence included, posted to an empty id and vanished. A quarter of the hub's first month of tasks were for problems already over. The window holds back the task ONLY: the investigation still starts on the first occurrence, so the diagnosis and the Slack card are immediate. Every other source projects on sight, AEGIS's own watchdogs included (`flow_health`, `delivery`, `social`, `drift`, `expiry`, `llm_governor`): they resolve what they stop finding, but their sweeps run every 30 minutes or hourly, so a three-minute window cannot observe a blip they would clear — it can only delay the task. The per-class seconds are the `hub_settle_seconds` settings row over the code defaults — and it is **one number with two jobs**: the same row sets the investigation's verification delay, so `{"*": 0}` buys back the immediate task at the price of every verification delay (a blip then costs a billed investigation and an auto-restart), which is not the same as the pre-#537 behaviour. **Every producer needs a way back, and alertmanager did not have one** (#551): it resolves a problem only on its `resolved` webhook and keeps its alerts in memory, so a restart loses the webhook and stranded the problem AND its task for good — the heartbeat re-checks and the watchdogs use `reconcile_findings`, but this lane had nothing. `HubSweepFlow` now asks alertmanager what it still holds (`hub_watch.reconcile_alertmanager`, `alertmanager_url` on the sweep's `activities.config`) and resolves what it no longer lists. It fails closed on every axis — unreachable, non-200, unreadable uptime, an alertmanager up under 15 minutes (a fresh one holds nothing until Prometheus re-sends, so reconciling then would close the estate), a problem whose LAST occurrence is under 10 minutes old, or a group — and the timeline says "no longer lists", never "cleared", because only the first is evidenced. **Judge a problem on EVERY fingerprint it has ever had, and on its LAST occurrence, never its first** (#561): an alertmanager fingerprint hashes the label set, so a recurring fault arrives under a new one each time (one prod problem had 26 across 27 occurrences), and the first version compared against a hash that could never be active again — it closed a live problem within a minute of every legitimate reopen, and its `first_seen_at` grace let a four-day-old problem that fired thirty seconds ago through. **A dead connector is a problem too, and one Slack ping is not a record** (#571): `services/connector_health.py` predates the hub, and all it did was post a single system event when a connector crossed its consecutive-failure threshold and then latch `alerted` so it never spoke again — one notification per outage, for the whole outage, with no problem, no task, no owner and nothing in any digest. Calibre was down two days at `{"alerted": true, "consecutive_failures": 3}`. It now also runs the connector set through `hub_watch.reconcile_findings` as `connectordown` findings (source `connector`, subject the connector name), so recovery resolves the problem instead of a flag deciding — a flag cannot tell "recovered" from "nobody looked", the absence of a finding can. `alerted` still suppresses repeat *pings* only. Two rules there: the sweep reads **every** `connector_health:*` row rather than the one being recorded, because `reconcile_findings` resolves any problem of its classes absent from the findings it is handed (so one connector's state would close every other connector's problem); and the row stores `down`, because the threshold is a per-call argument and a bare count says nothing about whether another connector is past its own. A deploy/maintenance window is a `service_state` row (`set_service_state` tool, `POST /api/hub/service-state`, the Ansible role); "Mute 24h" is `problems.muted_until`. **One outage is one problem** (#630). An alert's `aegis_class` label is its class, read before `alertname`, so Prometheus' `ServiceDownProlonged` (labelled `aegis_class: DockerServiceDown`) joins the `DockerServiceDown` problem instead of opening a second one. Class `outage` has no subject, so alertmanager's `ClusterOutage` and the heartbeat (`outage_min_nodes` not-ready nodes, default 2, on its `activities.config`) land on one problem. While it is live the hub keeps a `*`/`*` `service_state` row in state `outage`: infra sources (`hub.OUTAGE_SOURCES` — alertmanager, heartbeat, and the flow-health, delivery, drift and connector watchdogs) are recorded as `suppressed`, with no task and no investigation; money, research, feeds, chat, manual and Sentry are never held back, and neither is the outage itself. When it resolves the window ends `OUTAGE_TAIL` (10 min) later, never an operator's own window, and `HubSweepFlow` promotes what is still broken and starts the investigation the window held back (`promoted_investigations`). **One node down holds back only its own services** (#633). The heartbeat's NodeDown carries `services`: the replicated services with a live task on the node, from one `docker node ps` on the tick it goes down (global services are left out). While that `nodedown` problem is live the hub keeps one `service_state` row per service (`<service>`/`service`, state `outage`, `set_by = hub:<problem id>`), so their DockerServiceDown, ServiceDownProlonged and crash-loop problems, from alertmanager or the heartbeat (both use the swarm service name), are recorded as `suppressed`, and a service on another node is not. Prometheus' node alerts (`SwarmNodeNotReady` with `aegis_class: NodeDown`, and node-exporter's `NodeDown`) key on their `hostname` label, so they join the same `nodedown:node:<host>` problem; they carry no services and never change the rows. A resolve ends only the rows that problem set, with `OUTAGE_TAIL`. A hub row never replaces an operator's window that is still in force, and the sweep (`_reap_holds`) gives a tail to any hub row whose problem is gone. The cluster window is capped: it ends `OUTAGE_MAX` (6h) after the outage began, or began again after resolving, and a later occurrence never moves it; node rows are not capped. The heartbeat counts a node toward `outage_min_nodes` only if it went not ready within `outage_recent_hours` (default 6; `not_ready_since` in its state row), so noon being off for days no longer turns the next failure into an outage. **A card dies with its problem** (#629). Each run posts its own Gate-2 card, and an old card's **Run fix** used to keep working. Now a run retires the problem's older pending cards before it posts (`HubActivities.retire_cards`, reason `superseded`), and every resolve retires them inside the resolving transaction (`hub_cards.retire` from `ingest_event` and `set_status`). Retired means `interactions.status = 'retired'`, which the resolve endpoint refuses. The worker then edits the Slack message (edited, never deleted) and signals the waiting `InteractionFlow`: `superseded` ends the old run with no note, mute or record, and `self_resolved` takes the branch the escalating race always had. A card is found through its problem's `<run>:gate2` event, so runs waiting when this shipped are covered too. **One investigation per problem** (#639). A resolve and a new firing a second apart reopen a problem while its run is still going, and the reopen asks for a second one. Each run claims its problem at step 0 (`problems.investigation_run`, `hub.claim_investigation`, a compare-and-swap) and stands down, with a timeline line and no card, while Temporal says the holder is still RUNNING. Nothing clears the claim when a run ends, because a failed or cancelled run writes nothing either, so the describe is the only liveness test. The claim fails open: no client or an error means investigate. A run also asks `problem_status` once more right before its Gate-2 card, and posts none for a problem that resolved while it was investigating (`self_resolved_before_gate`). New producer = build an `Event`, call `ingest_event`, start the flow only when `investigate` is true — and add its source to `SOURCES`, which is a closed vocabulary that raises on anything else. **A `@code` task gets a problem too** — `hub_project.ensure_problem_for_task` mints a `manual` one, which is what gives a hand-written task a session registry (`work_sessions`), a timeline and a plan checklist; call it rather than writing a second "create a problem for this task" block.
- **The same failure on many entities is ONE problem** (`core/src/aegis/services/hub_group.py`). Six Postiz posts wedged in one queue were six problems and six Todoist tasks. A **group** problem carries `group_key = '{class}:{subject_kind}'` and a correlation key of `'{class}:{subject_kind}:*'`, and `ingest_event` gives it every later *occurrence* of that class whose own key has no problem — so the seventh stuck post joins the group instead of opening a seventh task. `HubSweepFlow` proposes one: `find_group_candidates` (three or more live, ungrouped problems of one class and kind) → `judge_group` (one billed `think()` call, NO_RETRY; a refusal or a failure leaves them separate) → `apply_group` (folds via `merge_problems`, retires the swallowed tasks, renames the survivor, says so in Slack). Three rules the code enforces rather than trusts: a group never spans classes; class `manual` is never groupable (those are hand-written tasks, and folding them would move one task's sessions and PR links onto another); and `hub_watch.reconcile_findings` resolves a group only when its watchdog stops finding **any** member, because a group's subject `*` is never among the findings. A "no" verdict is cached in `settings.hub_group_verdicts` until the cluster grows, so the sweep does not re-price the same question every five minutes.
